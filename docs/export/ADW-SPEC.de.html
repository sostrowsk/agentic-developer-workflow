Teil I — Philosophie

ADW existiert, weil agentisches Programmieren auf zwei vorhersehbare Arten scheitert: Der Agent bestimmt den Kontrollfluss (und dreht Schleifen, überspringt Prüfungen oder erklärt sich zum Sieger), und der Agent bewertet seine eigene Arbeit. Jedes der folgenden Prinzipien schließt eine dieser Türen. Jedes steht als Regel da, gefolgt vom Grund und der Stelle im Code, die es durchsetzt — ein Prinzip, das kein Code durchsetzt, ist nur ein Wunsch.

P1 — Kontrollfluss ist Code, nicht Prompt

Regel. Schleifen, Gates, Merges, Dispatch, Triage, Limits, Freigabepausen und CI-Polling sind deterministisches Python. Agents werden nur dort gerufen, wo Urteil nötig ist: Spec oder Plan schreiben, Code schreiben, ein Review beurteilen, einen Fehler einer Lane zuordnen.

Warum. Wiederholbare Arbeit im Prompt kostet Tokens, verhält sich jedes Mal anders und ist nicht testbar. Dieselbe Arbeit in Python kostet nichts, verhält sich identisch und ist durch Tests abgedeckt. Ein Agent mit der Anweisung „wiederhole, bis die Tests grün sind" kann zu früh aufhören, endlos laufen oder „grün" umdeuten; eine while-Schleife mit Zähler nicht.

Durchgesetzt durch. adw/phases.py besitzt jede Schleife; Agents bekommen einen einzelnen Task-String und liefern Text. Kein Agent wird je angewiesen, „jetzt die nächste Phase aufzurufen".

P2 — Reviewer fixen nie

Regel. Jeder Reviewer — Codex in Phase 1, 2 und 5, der Final-Reviewer in Phase 6, der E2E-Triage-Agent, der CI-Log-Analyst — ist read-only und antwortet nur mit Findings. Fixes macht immer der Build-Agent der betroffenen Lane.

Warum. Ein Reviewer, der „nur die Kleinigkeit" fixt, umgeht genau die Prüfungen, die seinen Fehler hätten finden sollen, und korrigiert seine eigenen Hausaufgaben. Die Trennung hält den Reviewer auch ehrlich: Er hat kein Interesse daran, dass der Code in Ordnung ist.

Durchgesetzt durch. Die Agent-Registry (adw/agents.py) gibt jedem Reviewer READ_ONLY_TOOLS (Read/Grep/Glob) und keine Schreibregel; Codex läuft mit --sandbox read-only.

P3 — Jeder Fix nimmt den validierten Weg

Regel. Ein Fix aus jeder Quelle (Gate-Fehler, E2E, Codex-Review, Final-Review, CI) läuft über den Build-Agent, dann durch alle Gates der Lane — und im Parallelmodus erneut durch Merge + E2E. Für kleine Fixes gibt es keine Abkürzung.

Warum. „Klein" ist die Meinung des Agents, keine Messung. Die Gates erneut laufen zu lassen kostet Sekunden bis Minuten; ein ungeprüfter Fix bis zum Push kostet eine rote Pipeline oder Schlimmeres.

Durchgesetzt durch. _dispatch_lane_fixes ist die einzige Fix-Routing-Funktion; sie endet immer in _run_lane (der Gate-Schleife). Die Review-Phasen holen ihren Worktree über _integration_loop, ein Review-Fix läuft also erneut durch Merge + E2E.

P4 — Alles ist begrenzt, und Stillstand wird erkannt

Regel. Jede Schleife hat ein hartes, persistiertes Limit. Zusätzlich stoppt ein Circuit-Breaker eine Schleife, sobald eine Runde exakt dieselbe Fehlermenge liefert wie die Runde davor.

Warum. Eine unbegrenzte Agent-Schleife ist der teuerste Fehlermodus überhaupt. Limits, die nur im Speicher leben, setzt ein Crash zurück — sie müssen mit der Arbeit persistiert werden, die sie bewachen. Der Circuit-Breaker fängt den billiger erkennbaren Fall — „nichts hat sich geändert" — lange bevor das Limit verbraucht ist.

Durchgesetzt durch. adw/triage.py (check_gate_iterations, check_fix_cycles, check_progress) und die Rundenzähler in RunState/LaneState. Limit-Prüfungen laufen vor der teuren Arbeit, nie danach.

P5 — Eskalation ist ein vollwertiges Ergebnis

Regel. Ein erschöpftes Limit, ein Merge-Konflikt, eine unlesbare Reviewer-Antwort oder eine verletzte Invariante beendet den Lauf kontrolliert: escalation.md + phase=escalated + Exit 1. Eskalierte Läufe sind endgültig.

Warum. Ein Orchestrator, der „irgendwie weitermacht", produziert teuren Müll. Ein Mensch bekommt den erreichten Stand und den konkreten Grund und entscheidet.

Durchgesetzt durch. escalate() in phases.py; adw resume verweigert eskalierte Läufe.

P6 — Fail fast, nie raten

Regel. Eine fehlende oder ungültige Config bricht ab, bevor irgendetwas startet; für Projektwissen (Gates, Branches, Lanes) gibt es keine geratenen Defaults. Parser akzeptieren genau eine wohldefinierte Form und lehnen alles andere ab.

Warum. Stille Defaults erzeugen stilles Fehlverhalten, und ein toleranter Parser akzeptiert im Zweifel ein veraltetes oder erfundenes ok. Ein Parse-Fehler ist sicher (Eskalation); ein falsches ok liefert kaputten Code aus.

Durchgesetzt durch. AdwConfig.load (strikter YAML-Loader, der doppelte Keys ablehnt, pydantic mit extra="forbid"); extract_review_result (JSON als Ganzes oder der letzte ```json-Fence, sonst nichts).

P7 — Prüfen statt vertrauen: Der Orchestrator hält die Beweise

Regel. Jede Behauptung, die ein Agent über seine eigene Arbeit aufstellen könnte, beweist stattdessen der Orchestrator und persistiert sie in eigenem State: Gates grün (gates_passed + gates_tree-Hash), RED bewiesen (red_confirmed + red_test_paths), HEAD unverändert (expected_head), Branch unverändert. Nur der Orchestrator committet.

Warum. Eine vom Agent geschriebene Commit-Message, ein Flag oder Report ist vom Agent fälschbar. Ein vom Orchestrator berechneter Tree-Hash bindet „die Gates waren grün" an genau den geprüften Inhalt. Dieselbe Begründung lehnt Task-Selbstauskunft im Trace ab (docs/SPEC.md §6).

Durchgesetzt durch. _worktree_tree_hash, _require_no_agent_commit, _require_lane_branch, _require_expected_head, _commit_lane in phases.py.

P8 — Minimale Rechte für Agents

Regel. Jeder Agent bekommt die kleinste Tool-Menge und die engsten Pfadregeln, mit denen er seine Aufgabe erledigen kann. Secret-Stores sind für alle gesperrt, Run-State ist für alle unbeschreibbar, Nachbar-Lanes sind unlesbar, Bash läuft in der Sandbox. Subprozesse erben nur eine Whitelist der Umgebung.

Warum. Agents lesen nicht vertrauenswürdige Inhalte (Issue-Text, Repo-Dateien, CI-Logs). Was auch immer eine eingeschleuste Anweisung sie tun lassen könnte — die Tool-Grenze begrenzt den Schaden.

Durchgesetzt durch. AgentSpec.tools (beschränkt das Angebot) + allowed_tools (artefaktgenaue Pfadregeln), SECRET_STORE_DENY_RULES, sandbox_bash, deny_read_paths pro Lane, safe_env(); geschützte Artefakte werden nach jedem Agent-Lauf byte-genau wiederhergestellt.

P9 — Abrechnung über den Plan, nie über den API-Zähler

Regel. ADW spricht mit Claude ausschließlich über die Claude-Code-CLI (vom Agent SDK headless gestartet) mit gespeichertem Login. API-Key-Umgebungsvariablen werden aktiv geleert. Ein fehlgeschlagener Agent-Aufruf — typischerweise ein erschöpftes Plan-Fenster — lässt den Lauf an seinem Checkpoint stehen, ohne zu eskalieren; adw resume setzt nach dem Reset fort.

Warum. Kostenkontrolle per Konstruktion statt per Disziplin: Ein versehentliches tokenweises API-Budget-Leerlaufen ist technisch unmöglich. Der Preis ist ein Verfügbarkeitsrisiko, das die Crash-Resume-Konstruktion ohnehin abdeckt.

Durchgesetzt durch. _require_stored_login() und die Env-Overrides in adw/agents.py; der AgentRunError-Zweig in cli._execute.

P10 — Crash-sicher per Konstruktion

Regel. Jeder Übergang und jedes offene Feedback wird atomar gecheckpointet. Budget-Erhöhungen werden im selben Save persistiert wie die Arbeit, die sie rechtfertigt. Billig wiederherstellbarer Zustand (Integrations-Branch, Review-Worktrees) wird weggeworfen und neu gebaut statt interpretiert.

Warum. Echte Läufe dauern Stunden, laufen in Plan-Limits und werden gekillt. Einen halb gemergten oder halb geschriebenen Zustand korrekt zu interpretieren ist fehleranfällig; ihn deterministisch neu aufzubauen ist billig und beweisbar korrekt.

Durchgesetzt durch. RunState.save/update (tmp + os.replace, flock), den mutate_staged-Hook in _dispatch_lane_fixes, _fresh_integration_worktree, _resume_pending_lanes.

P11 — Ein Codepfad; der Dry-Run ist ein Produkt-Feature

Regel. Der Single-Lane-Modus ist der Parallelmodus mit einer Lane — es gibt einen Codepfad und eine CLI. --dry-run injiziert Mocks in den produktiven Codepfad, inklusive kanonischer Fehler-Fixtures (ein Gate, das erst im zweiten Versuch grün wird; ein E2E-Fehler, den ein triagierter Lane-Fix behebt).

Warum. Zwei Codepfade driften auseinander. Ein Dry-Run, der den echten Kontrollfluss durchläuft, lässt Anwender eine Config und den ganzen Ablauf für 0 Tokens abnehmen und gibt den Abnahmetests etwas Echtes zu prüfen.

Durchgesetzt durch. RunContext als Dependency-Injection-Wurzel (aller Kontakt mit der Außenwelt läuft darüber); cli._dry_run_runners/_dry_run_glab/_dry_run_gh.

P12 — Tests sind reine Mocks, git ist echt

Regel. Kein Test braucht Netzwerk oder Tokens. Agents, Codex, glab und gh werden an ihren Schnittstellen gemockt; git ist echt (Wegwerf-Repos in tmp_path). Entwickelt wird test-first: ein roter Test vor jeder Verhaltensänderung, ein Regressionstest zu jedem Bugfix.

Warum. Die härtesten Garantien des Orchestrators betreffen git-Zustand, Crash-Fenster und Worktrees — git zu mocken hieße, den Mock zu testen. Die externen Dienste sind der Ort von Kosten und Flakiness.

Durchgesetzt durch. adw/mock.py (MockAgentRunner, MockCodexRunner); die injizierbaren Seams run_glab/run_gh/sleep; ein JS-Harness, der das ausgelieferte app.js in reinem node treibt, für die GUI.

P13 — Review-Loops konvergieren per Policy: absteigende Severity, Findings-Gedächtnis, Cap 5

Regel. Jeder Codex-Review-Loop — Authoring (Spec/Plan) und Code-Review — folgt derselben Policy:

Runde Bearbeitete Findings Übrige
1 P1, P2, P3 —
2 P1, P2 P3 → Known Limitations / Follow-ups
≥ 3 nur P1 P2, P3 → Known Limitations / Follow-ups
Cap 5 offenes P1 → Eskalation alles andere akzeptiert und dokumentiert

Ab Runde 2 bekommt Codex die Findings der Vorrunden mit ihrer Disposition (umgesetzt / abgewiesen + Grund / unter der Schwelle), damit erledigte Punkte nicht erneut gemeldet werden.

Warum. Ohne diese Policy konvergiert der Loop bei Orchestrierungscode nicht: Ein deterministischer Reviewer findet einen unbegrenzten Vorrat an Randfällen auf der niedrigsten Severity, und ohne Gedächtnis pendelt er zwischen „zu strikt" und „zu tolerant". Dieselbe Policy ist die Review-Regel der Contributors pro Commit — ADW und seine Entwickler fahren bewusst denselben Loop.

Durchgesetzt durch. _actionable_severities, _split_by_severity, _severity_context, AUTHORING_MAX_ROUNDS = 5, MAX_REVIEW_ROUNDS = 5 in phases.py; Dispositionen persistiert in authoring_prior_context / review_prior_context.

P14 — Verhältnismäßigkeit: bauen, was das Issue verlangt

Regel. Spec- und Plan-Autoren sind an eine Verhältnismäßigkeitsregel gebunden: Jedes Akzeptanzkriterium muss sich auf das Issue zurückführen lassen; Prozessvorgaben (Commit-Messages, Branch-Topologie, git-Historie) gehören nicht in eine Spec. Am Ende gefundene Scope-Lücken werden Follow-ups, keine neue Arbeit.

Warum. Zwei starke Autoren plus ein strenger Reviewer blähen den Scope naturgemäß auf. Das Gegengewicht muss in den Prompts beider Autoren und der Synthese stehen, sonst macht die Synthese es rückgängig.

Durchgesetzt durch. _SPEC_CONTENT_RULES / _PLAN_CONTENT_RULES — je eine geteilte Konstante, genutzt vom Claude-Autor, vom Synthese-Agent und in den Codex-Autor-Prompts; scope_gap-Triage nach followups.md.

P15 — Doku ist zweisprachig und mit dem Code versioniert

Regel. Alle Doku existiert auf Englisch (Default, ohne Suffix) und Deutsch (.de. vor der Endung), synchron gehalten, mit Sprachumschalter unter der H1. Jeder Push nach main ist ein Release mit Versionssprung, Changelog-Eintrag in beiden Sprachen und Tag (siehe §18).

Warum. Anwender und Contributors arbeiten in beiden Sprachen; eine Doku, die es nur in einer gibt, veraltet still in der anderen. Releases pro Push halten die Frage „welche Version hat das eingeführt?" beantwortbar.

1.1 RunContext — die Dependency-Injection-Wurzel

RunContext (Dataclass in phases.py) trägt alles, was eine Phase braucht: repo, config, state, die beiden Runner-Schnittstellen (agents: AgentRunner, codex: CodexClient), die Seams run_glab, run_gh, sleep, den einen emitter des Laufs, die gepinnten Flags skip_approval, spec_approval, dry_run, ein git_env und ein threading.RLock (state_lock), das State-Mutationen über parallele Lane-Threads serialisiert. ctx.save() persistiert den State und spiegelt nach erfolgreichem Schreiben ein state.saved-Event.

Weil jeder Kontakt mit der Außenwelt über dieses Objekt läuft, läuft derselbe produktive Code im --dry-run und in der Testsuite gegen Mocks.

1.2 Die beiden Urteils-Schnittstellen

class AgentRunner(Protocol):
    def run(self, agent: AgentSpec, task: str, cwd: Path, resume: str | None = None,
            deny_read_paths: list[str] | None = None, emitter=None, span=None,
            on_session_id=None) -> AgentResult: ...          # AgentResult(text, session_id)

class CodexClient(Protocol):
    def review(self, kind, content_refs, cwd, context=None, emitter=None, span=None) -> ReviewResult: ...
    def author(self, kind, task, cwd, marker_id=None, emitter=None, span=None) -> dict[str, str]: ...
                                                     # Dateiname → Inhalt; kind: spec | plan

on_session_id lässt den Runner die SDK-Session-ID melden, sobald sie im Stream erscheint — ein Crash mitten im Lauf hinterlässt so trotzdem eine fortsetzbare Session im State.

2. Zustandsautomat

  run ──────▶│     spec     │─────────────────────▶│ awaiting_spec_approval │──approve──┐
             └──────┬───────┘                      └────────────────────────┘           │
                    │ (kein Spec-Gate)                                                  ▼
                    └────────────────────────────────────────────────────────────▶┌──────┐
                                                                                  │ plan │
             ┌──────────────────────────┐  --gates plan|both (Default: plan)      └──┬───┘
             │    awaiting_approval     │◀───────────────────────────────────────────┘
             │(Plan-Gate oder Breakpoint)│──approve──▶ build ─▶ [before_integration] ─▶
             └──────────────────────────┘
        integration ─▶ codex_review ─▶ final_review ─▶ [before_push] ─▶ ci ─▶ done

  jede Phase ──(Limit / Konflikt / Parse-Fehler / Invariante)──▶ escalated   (endgültig)
  jede Phase ──(AgentRunError, Crash, Kill)──▶ Phase unverändert, fortsetzbar mit `adw resume`
  • Phase ist ein geschlossenes Literal in state.py: spec, awaiting_spec_approval, plan, awaiting_approval, build, integration, codex_review, final_review, ci, done, escalated.
  • Breakpoints (before_integration, before_push) nutzen awaiting_approval mit; welcher wartet, steht in pending_breakpoint — kein neuer Phasenwert. Sie halten nur, wenn sie in der Config aktiviert sind und die Freigabe nicht übersprungen wird (--gates none überspringt auch sie).
  • cli._execute ruft immer die komplette Phasenkette; jede Phasenfunktion prüft ctx.state.phase selbst und kehrt sofort zurück, wenn sie nicht dran ist. Ein Resume startet dadurch ohne Dispatcher in der richtigen Phase.
  • Exit-Codes: 0 fertig · 2 wartet auf Freigabe (Gate oder Breakpoint) · 1 Eskalation, Verweigerung oder abgebrochener Agent-Aufruf (die Meldung unterscheidet sie).

3. Kontrollfluss der Phasen (Übersicht)

Die Phasen erklärt Schritt für Schritt der ADW-Workflow. Die Verträge, die ein Contributor erhalten muss:

Phase Funktion Vertrag
1–2 Spec, Plan run_spec_and_plan → _draft_stage, _reviewed_authoring_loop Claude-Autor (Opus) und Codex-Autor schreiben parallel Entwürfe nach .adw/runs/<id>/drafts/; idempotent über die Dateien; ein Codex-Fehler degradiert (Marker <kind>.codex.FAILED), ein fehlender Claude-Entwurf eskaliert. Der Synthese-Agent (Fable) ist Runde 1 des Authoring-Loops und schreibt zusätzlich die Gate-Zusammenfassung. Schleife: Codex-Review → Findings an dieselbe Session → P13-Policy, Cap 5. Geschützte Dateien nach jedem Lauf wiederhergestellt; Artefakte ins Run-Verzeichnis archiviert, Checkout zurückgesetzt.
Gates cli._execute / cli.approve Spec-Gate (optional), Plan-Gate (Default), im State persistiert; awaited/granted-Approval-Events.
3 Build run_build_phase → _run_lane Pro Lane: Worktree, Artefakte einspielen + Orchestrator-Commit, optionale RED-Stufe (_confirm_red), Gate-Schleife (Limit → Checkpoint → Agent → Invarianten → Restore → Gates), Beweis mit Tree-Hash, Orchestrator-Commit. Lanes laufen unter --parallel in einem Thread-Pool.
Breakpoint _breakpoint_gate("before_integration") Halt, nachdem alle Lanes grün sind.
4 Integration run_integration_phase → _integration_loop Integrations-Branch jede Runde frisch vom Base-Branch; Merge-Konflikt → Abort + Eskalation; E2E-Gate mit den Ports beider Lanes; rot → Triage-Agent → Lane-Fixes → neu integrieren. Nur im Parallelmodus.
5 Codex-Review run_codex_review_phase Zuerst _resume_pending_lanes (kein ungegateter Stand erreicht ein Review); Limit-Prüfung vor dem Dispatch; Circuit-Breaker auf der bearbeitbaren Finding-Menge; P13-Policy; verworfene Findings → followups.md.
6 Final-Review run_final_review_phase Fable, read-only, Pflichtfeld category; triage_final_review leitet scope_gap → Follow-ups, Rest → Fix-Zyklen (max. 3 pro Lane); Zyklus-Erhöhung mit dem vorgemerkten Fix persistiert.
Breakpoint _breakpoint_gate("before_push") Halt vor jeder Push-/CI-Arbeit.
7 CI run_ci_phase git push --force-with-lease -u origin <branch> (Integrations-Branch im Parallelmodus, sonst Lane-Branch; im Dry-Run übersprungen); SHA-gebundenes Polling; rot mit Logs → Log-Analyst → genau ein Re-Entry; rot ohne Logs → Eskalation.

4. Datenmodell

4.1 Config im Ziel-Repo — .adw/config.yaml

Geladen von AdwConfig.load(repo). Strikt: doppelte YAML-Keys, unbekannte Keys (extra="forbid"), leere Strings, nicht-positive Timeouts und nicht-boolesche tdd-Werte sind ein ConfigError, bevor irgendetwas läuft.

4.3 Findings — der eine Reviewer-Vertrag

Jeder Reviewer (Codex, Final-Reviewer, E2E-Triage, Log-Analyst) antwortet im selben Schema, eingebettet über die geteilte Konstante SCHEMA_INSTRUCTION:

{
  "verdict": "ok | needs_fixes",
  "findings": [{
    "severity": "P1 | P2 | P3",
    "lane": "frontend | backend | unknown",
    "file": "pfad/relativ/zum/repo",
    "issue": "Beschreibung",
    "remediation_plan": ["Schritt 1", "Schritt 2"],
    "category": "scope_gap | implementation | trivial"
  }]
}
  • extra="forbid"; ok nur mit leerer Liste, needs_fixes mit ≥ 1 Finding.
  • category ist für den Final-Reviewer Pflicht (fehlt sie → Eskalation, kein stiller Default), sonst optional.
  • Der Parser akzeptiert nur eine Antwort, die als Ganzes JSON ist, oder den Inhalt des letzten ```json-Fence. Doppelte Keys, Verschachtelung > 100 und Integer > 100 Stellen scheitern geschlossen in linearer Zeit. Schema-Verletzungen (ValidationError) eskalieren wie Parse-Fehler.
  • Die Identität eines Findings für Circuit-Breaker, Vertagung und Dispositionen ist der Key "<file>|<issue>".
  • Ein Lane-Wert unknown oder eine in diesem Lauf inaktive Lane geht an alle aktiven Lanes — lieber doppelt geprüft als verloren.

4.5 Event-Log

.adw/runs/<run_id>/events.jsonl, ein JSON-Objekt pro Zeile:

{"seq": 17, "ts": "2026-09-13T10:02:03.123Z", "type": "gate", "kind": "start|end|point",
 "span": "<id>", "parent": "<id|null>", "phase": "build", "lane": "backend",
 "round": null, "payload": {...}}
  • Span-Typen: run, phase, lane, round, agent.run, gate, codex.review, codex.author, ci.wait.
  • Punkt-Typen: agent.message, agent.tool.call, agent.tool.result, snapshot, red.check, commit, merge, ci.poll, ci.reentry, triage.decision, limit.hit, circuit_breaker, escalation, approval, artifact, followup, state.saved, log.
  • Die Payloads spezifiziert GUI-SPEC.de.md §4.4. Der Start von agent.run trägt den vollständigen Prompt; das Log enthält daher unredigierte Agent-Ein- und -Ausgaben und wird mit Modus 0600 angelegt.
  • Fail-open ist die bestimmende Invariante: Kein Emitter-Fehler (Platte voll, Rechte, nicht serialisierbare Payload) erreicht je den Aufrufer. Beim ersten internen Fehler warnt der Emitter einmal und schaltet sich für diesen Lauf ab. state.json — nicht das Event-Log — ist die Resume-Autorität, deshalb wird bewusst kein fsync ausgeführt.
  • seq wird unter flock prozessübergreifend vergeben; eine durch Crash abgeschnittene letzte Zeile wird geheilt, indem der nächste Record auf einer frischen Zeile beginnt.
  • In Worker-Threads geöffnete Spans (parallele Lanes, Entwurfs-Pool) tragen parent: null; das GUI-Modell hängt sie über zeitliches Enthaltensein ein.

4.6 Snapshots

An jeder Schrittgrenze einer Lane (before_agent, after_agent, after_gates, red) baut snapshots.capture() einen Tree über einen temporären Index, erzeugt mit commit-tree -p <base_sha> ein Commit-Objekt, pinnt es als refs/adw/<run_id>/<seq> und emittiert ein snapshot-Event. Die GUI berechnet Schritt-Diffs bei Bedarf aus diesen Refs; ins Log wird nie ein Diff geschrieben. Fail-open wie der Emitter.

5. Agent-Registry

Jeder Agent ist eine eingefrorene AgentSpec(name, model, tools, allowed_tools, system_append, permission_mode="default", sandbox_bash=False). tools beschränkt, was dem Agent überhaupt angeboten wird; allowed_tools genehmigt (pfadbeschränkt). Beides ist nötig.

Agent Modell Tools Schreibregeln Auftrag
spec_agent Opus 4.8 Read/Grep/Glob/Write/Edit .adw/spec.md Spec-Entwurf (Ziel, Scope, Nicht-Ziele, Akzeptanzkriterien, DoD)
plan_agent Opus 4.8 dito .adw/plan.md, .adw/contract.yaml Plan-Entwurf mit ## Workstream:-Abschnitten + Kontrakt
spec_synthesis Fable 5 dito .adw/spec.md, .adw/spec-summary.md Best-of-Merge beider Entwürfe + Gate-Zusammenfassung
plan_synthesis Fable 5 dito .adw/plan.md, .adw/contract.yaml, .adw/plan-summary.md Best-of-Merge + Gate-Zusammenfassung
build_agent Opus 4.8 + Bash (Sandbox) ./** (worktree-relativ) Setzt seinen Workstream gegen den Kontrakt um, TDD; committet nicht; darf mit Begründung von Fix-Plänen abweichen
e2e_triage Sonnet 5 Read/Grep/Glob — Ordnet E2E-Fehler Lanes zu; nur Findings-JSON
log_analyst Sonnet 5 Read/Grep/Glob — CI-Logs → Findings mit Lane; nur Findings-JSON
final_reviewer Fable 5 Read/Grep/Glob — Implementierung gegen Spec; Findings mit Pflichtfeld category

Modell-IDs sind Konstanten in agents.py: FABLE = "claude-fable-5", OPUS = "claude-opus-4-8", SONNET = "claude-sonnet-5".

Modell-Ökonomie. Opus macht die tiefe Arbeit (Entwürfe, Build). Fable — breiter und günstiger — führt Entwürfe zusammen und reviewt das Ergebnis. Sonnet erledigt die Fließband-Triage.

Geteilte Prompt-Konstanten. _SPEC_CONTENT_RULES, _PLAN_CONTENT_RULES, _BEST_OF_MERGE_RULES, _SUMMARY_FORMAT_RULES existieren einmal und werden von jedem Agent wiederverwendet, der sie braucht, einschließlich der Codex-Autor-Prompts — drifteten sie auseinander, würde die Synthese das Verhältnismäßigkeits-Gegengewicht des Autors kippen.

Regeln für jeden Agent.

  • Leseregeln sind auf das cwd beschränkt (Read(./**), …).
  • Schreibregeln sind artefaktgenau (Write(.adw/spec.md), nie .adw/** — das machte state.json beschreibbar).
  • SECRET_STORE_DENY_RULES: ~/.ssh, ~/.aws, ~/.claude, ~/.gnupg, ~/.config, ~/.docker, ~/.kube, ~/.azure, ~/.codex, Credential-Dateien sowie Shell-Startup- und History-Dateien sind unlesbar; .adw/runs/** ist unbeschreibbar. Deny schlägt Allow. Jeder Store steht als Glob und als einfaches Verzeichnis darin, weil die Linux-Sandbox reine Glob-Denies ignoriert.
  • Unter --parallel bekommt jede Lane die Worktrees der anderen Lanes als deny_read_paths.

SdkAgentRunner. Baut ClaudeAgentOptions mit dem System-Prompt-Preset claude_code + system_append, cwd, resume, setting_sources=[] und strict_mcp_config=True (keine repo-gesteuerten Hooks, Settings oder MCP-Server) und — für sandbox_bash-Agents — eine Sandbox mit allowUnsandboxedCommands: False ohne ausgenommene Kommandos (auch git bleibt in der Sandbox). Er spiegelt Assistant-Text und Tool-Aufrufe/-Ergebnisse ins Event-Log und summiert Kosten/Tokens in RunTotals.

6. Gate-Runner

run_gates(gates, cwd, extra_env, emitter) → GateReport:

  • Gates laufen in Config-Reihenfolge, Fail fast beim ersten Fehler.
  • Jedes Gate ist ein Subprozess mit safe_env(extra_env) (Lane-Ports kommen als Extra-Env), dem Config-Timeout, start_new_session=True und Prozessgruppen-Kill auf jedem Ausgangspfad — keine verwaisten Kindprozesse.
  • Die Ausgabe sammeln Pump-Threads in einen RAM-begrenzten Tail: höchstens 200 Zeilen à höchstens 4 KiB. Diesen Tail sieht der Build-Agent als Fix-Task (die RED-Stufe kürzt ihn weiter auf 40 Zeilen).
  • Jedes gestartete Gate ist ein gate-Span (passed, exit_code, timed_out, output).

7. Codex-Integration

CodexRunner startet codex exec --sandbox read-only -c mcp_servers={} … als Subprozess mit:

  • einem isolierten CODEX_HOME — ein Temp-Verzeichnis, das nur eine Kopie von auth.json aus dem echten Home enthält, damit nutzerkonfigurierte MCP-Server und Settings draußen bleiben. Ein während des Aufrufs rotiertes Token wird per Compare-and-Swap unter flock zurücksynchronisiert.
  • dem konfigurierten Timeout (codex.timeout, Default 900 s) und Prozessgruppen-Kill.
  • begrenzten Puffern für stdout (5-MiB-Tail) und stderr (256-KiB-Tail).

review(kind, content_refs, cwd, context) — kind ist spec, plan oder code; der Prompt bettet SCHEMA_INSTRUCTION ein; die Antwort wird mit extract_review_result geparst. Ab Runde 2 trägt context die Severity-Schwelle und die Dispositionen der Vorrunden.

author(kind, task, cwd) — die Read-only-Sandbox kann nicht schreiben, also muss Codex Dateiinhalte in Marker-Blöcken ===BEGIN <name> <nonce>=== … ===END <name> <nonce>=== mit frischer Nonce pro Aufruf liefern. Geparst wird ab dem letzten Begin-Marker des ersten Namens; ein bloßes Prompt-Echo ergibt leere Blöcke und löst CodexAuthorError aus. Der Orchestrator schreibt den gelieferten Inhalt ins Entwurfsverzeichnis.

8. CI- und Forge-Abstraktion

  • forge.detect_forge(repo, override) → "gitlab" | "github": Der Key ci.provider gewinnt; sonst der Hostname der origin-URL; unbekannter Host → ForgeError, der in einem echten Lauf Phase 7 eskaliert (kein Polling gegen die falsche API). Der Dry-Run fällt auf GitLab zurück.
  • GitLab (ci.py): glab api projects/:id/pipelines?ref=…&sha=… — die Pipeline wird serverseitig über den gepushten SHA abgefragt, sodass weder eine ältere terminale noch eine fremde neuere Pipeline mit der gesuchten verwechselt werden kann. Terminale Status: success, failed, canceled, skipped. Ein optionaler staging_job muss zusätzlich grün sein. Logs fehlgeschlagener Jobs kommen als 200-Zeilen-Auszug.
  • GitHub (github.py): alle Workflow-Runs des Push-SHA (actions/runs?head_sha=…), bis alle abgeschlossen sind; grüne Conclusions sind success, skipped, neutral; rote Runs liefern gh run view --log-failed-Auszüge.
  • Beide liefern dasselbe CiResult und werfen dieselben CiError/CiTimeoutError. Das Zeitbudget wird als Restzeit geführt, der Sleep darauf gedeckelt. run_glab/run_gh/sleep sind injizierbare Seams mit 120-s-Subprozess-Timeouts.
  • Eine Forge hinzufügen: ein poll_ci(repo, branch, cfg, run_x, sha, emitter) implementieren, das CiResult liefert; das Forge-Literal und detect_forge erweitern; den Providerwert in CiConfig.provider ergänzen; in run_ci_phase verdrahten; einen Dry-Run-Fake in cli.py und — falls die Forge Issues hat — einen Issue-Abruf ergänzen.

9. Semantik von Resume, Freigabe und Nebenläufigkeit

  • adw resume <run_id> setzt genau am persistierten Checkpoint fort. Eskalierte Läufe verweigert es. Es lädt den State unter dem Ausführungs-Lock des Laufs neu, löst die Config über _config_for_continuation auf (gepinnter Base-Branch und gepinnte Breakpoints schlagen die aktuelle Datei; --base-branch ist nur vor Anlage der Lanes änderbar), fährt den Arbeitsbaum-Vorflug und dann _execute.
  • adw approve <run_id> gilt nur in awaiting_approval / awaiting_spec_approval. Unter demselben Lock lädt es neu und validiert erneut, sodass zwei gleichzeitige Freigaben genau eine Freigabe und eine nachgelagerte Ausführung ergeben (ein doppelter Push bei before_push ist ausgeschlossen). Eine Breakpoint-Freigabe schaltet die Phase weiter und leert pending_breakpoint in einem atomaren Save; das granted-Event emittiert _catch_up_granted_breakpoints log-geprüft, was das Crash-Fenster zwischen Save und Log-Append ohne zusätzliches State-Feld schließt.
  • Arbeitsbaum-Vorflug (run, resume, approve): Ein sauberer Checkout geht weiter; besteht die Dirty-Menge ausschließlich aus den sechs ADW-Authoring-Artefakten, wird sie aus HEAD geheilt (git checkout HEAD -- <pfad>, bzw. Index-Eintrag entfernt + Datei gelöscht, wenn nicht in HEAD) und erneut geprüft; jede fremde Änderung verweigert das Kommando und verwirft nichts. Der Vorflug eskaliert nie.
  • Abgebrochene Agent-Aufrufe (AgentRunError) lassen die Phase unverändert und geben einen Resume-Hinweis aus (P9).
  • Session-Resume: Fix-Tasks gehen an dieselbe SDK-Session (resume=session_id); die Session-ID wird gecheckpointet, sobald sie erscheint.
  • Revalidierung: Vor jeder Review-Phase schickt _resume_pending_lanes jede Lane durch _run_lane — unfertige Fixes holen auf, fertige Lanes werden gegen gates_tree revalidiert; eine Lane, deren Tree nicht mehr passt, geht zurück in die Schleife.

10. Beobachtbarkeit, Retention und Registry

  • Retention (adw runs list, adw runs prune [--keep N] [--older-than TAGE] [--gzip] sowie Auto-Prune mit trace.keep_runs, nachdem ein Lauf done erreicht): Nur done-/escalated-Läufe sind Kandidaten; ein Lauf mit uncommitteten Änderungen in irgendeinem Worktree wird übersprungen und benannt; Löschreihenfolge Worktrees (über git's Worktree-Verwaltung, Lane-Branches bleiben) → Snapshot-Refs → Verzeichnis; --gzip komprimiert das Event-Log atomar und lässt den Lauf vollständig. Auto-Prune ist fail-open: Es ändert nie Phase oder Exit-Code des fertigen Laufs.
  • Registry ~/.adw/repos.json (Version 1): kanonischer Repo-Pfad → stabiler, URL-sicherer Slug + last_seen. Atomar geschrieben; adw run registriert automatisch, fail-open.

11. GUI-Architektur (Run Inspector)

Normativ spezifiziert ist die GUI in docs/GUI-SPEC.de.md; dieser Abschnitt legt nur die Architekturgrenzen fest, die ein Kern-Contributor nicht brechen darf.

  • Optionales Extra. FastAPI, uvicorn, Jinja2, markdown-it-py liegen im Extra gui. Der Kernpfad adw run importiert sie nie; adw gui importiert lazy und gibt einen Installationshinweis aus, wenn sie fehlen.
  • Strikt read-only. Keine Schreibroute, kein externes Programm, liest nur unter .adw/runs/<run_id>/, die Registry und seine paketierten Assets. Diffs nur über eine explizite Ref-Allowlist.
  • Standardmäßig Loopback. Ein Nicht-Loopback---host verlangt --i-know, weil das Event-Log unredigierte Agent-Ausgaben enthält.
  • Schichten. reader (inkrementell, tolerant) → model (Span-Baum) → app (abgeleitete Sichten: Trace-Baum, Timeline, Lauf-Kontext, Recovery-Karte, Plan-Skelett, Änderungsumfang, Kennzahlen). Alles Angezeigte ist aus Event-Log, State und Artefakten abgeleitet — die GUI fügt kein Event, keine Persistenz und keine Sidecar-Datei hinzu.
  • Robustheitsgarantie. Eine kaputte oder nicht-Mapping-Payload ergibt nie einen 5xx; jeder Lesezugriff läuft über _as_mapping() / _mapping_payload().
  • Routen. /, /runs/{repo}/{run_id} sowie /api/runs, /api/runs/{repo}/{run_id}, …/events, …/diff, …/artifacts/{name}, …/stream (SSE). Änderungen an der JSON-API sind nur additiv.
  • Vertrag für Kern-Contributors: Wer einen Event-Typ oder ein Payload-Feld hinzufügt, aktualisiert GUI-SPEC.md §4.4 und stellt sicher, dass unbekannte Typen weiterhin als generische Knoten erscheinen. Emitter und Snapshotter dürfen nie einen Lauf scheitern lassen können.

12. Sicherheitsmodell

Schicht Mechanismus
Agent-Tools tools beschränkt das Angebot; allowed_tools mit artefaktgenauen Pfadregeln; Reviewer strikt read-only; Build-Bash in der Sandbox, kein Ausweg ohne Sandbox.
Secrets SECRET_STORE_DENY_RULES für jeden Agent; safe_env()-Whitelist (PATH, HOME, USER, SHELL, TERM, TMPDIR, LANG, LANGUAGE, TZ, VIRTUAL_ENV, PYTHONPATH, NODE_ENV, CI, CLAUDE_CONFIG_DIR, LC_*) für jeden Subprozess. Das SDK merged os.environ, daher werden nicht gelistete Variablen per ""-Override geleert. CODEX_HOME erreicht nur den Codex-Runner.
Auth & Abrechnung Nur gespeicherter Claude-CLI-Login (_require_stored_login(), Fail fast, bevor Tokens fließen); ANTHROPIC_API_KEY & Co. geleert. Codex mit isoliertem CODEX_HOME.
Settings-Isolation setting_sources=[], strict_mcp_config=True für Agents; mcp_servers={} für Codex — das Ziel-Repo kann keine Hooks, Settings oder MCP-Server einschleusen.
git-Integrität Orchestrator-git läuft mit core.hooksPath=/dev/null und der Env-Whitelist. Nur der Orchestrator committet; Agent-Commits, Branch-Wechsel und HEAD-Bewegungen über ein Crash-Fenster werden erkannt und eskalieren.
Artefakt-Integrität config.yaml und ab Phase 2 die reviewte Spec (ab Phase 3 Spec/Plan/Kontrakt) werden nach jedem Agent-Lauf byte-genau wiederhergestellt; Symlink-/Verzeichnis-Ersetzungen werden erkannt und ersetzt, nie verfolgt.
Lane-Isolation Ein Worktree pro Lane, Nachbarn unlesbar, deterministische Ports (backend 9100–9149, frontend 9200–9249, Offset aus der Run-ID) mit Bind-Check.
Datenschutz Event-Log Modus 0600, .gz erbt ihn; GUI standardmäßig nur Loopback.

13. Invarianten

Contributors müssen alle diese Aussagen wahr halten. Die meisten haben eigene Tests.

  1. I1 Nur der Orchestrator committet. Jeder Commit eines Agents eskaliert.
  2. I2 Kein Stand erreicht ein Review, einen Merge oder einen Push ohne grüne Gates, gebunden an seinen aktuellen Tree-Hash.
  3. I3 Jede Schleife prüft ihr Limit bevor sie die teure Arbeit macht.
  4. I4 Jede Budget-Erhöhung wird im selben Save persistiert wie die Arbeit, die sie bezahlt.
  5. I5 Circuit-Breaker-Basen rücken erst nach dem Fix-Dispatch vor.
  6. I6 Reviewer-Ausgaben werden strikt geparst; jede unlesbare oder schemawidrige Antwort eskaliert — nie ein Default ok.
  7. I7 Geschützte Artefakte und die Config sind nach jedem Agent-Lauf byte-gleich.
  8. I8 Run-Start-Entscheidungen (Base-Branch, Breakpoints, Gate-Modus, Dry-Run) sind im State gepinnt; eine Fortsetzung liest sie nie erneut aus der CLI oder einer geänderten Config.
  9. I9 Eskalation ist endgültig; ein abgebrochener Agent-Aufruf ist keine Eskalation.
  10. I10 Event-Log, Snapshots, Registry und Auto-Prune sind fail-open und ändern nie das Ergebnis eines Laufs.
  11. I11 Der Vorflug verwirft nie fremde Änderungen und eskaliert nie.
  12. I12 Die GUI schreibt nie und liefert für kaputte Log-Daten nie einen 5xx.
  13. I13 Die Kerninstallation importiert nie den Web-Stack.
  14. I14 Kein Subprozess läuft ohne Timeout oder mit voller Umgebung.

16. Teststrategie und Entwicklungsablauf

  • Suite: 1278 Tests in tests/ (Stand 0.26.1), test-first entwickelt, reine Mocks, echtes git. Ausführen mit uv run pytest. Die CI (.github/workflows/ci.yml) fährt uv sync --locked, uv run ruff check ., uv run pytest -q mit NO_COLOR=1.
  • Mock-Rückgrat: MockAgentRunner (Antwort-Queues pro Agent, Dateiausgaben als statische Map oder Callable(cwd), vollständige Aufrufaufzeichnung inkl. resume und deny_read_paths), MockCodexRunner (Review- und Autor-Queues).
  • Crash-Fenster: Viele Phasentests manipulieren den State zwischen zwei Checkpoints, „killen" den Prozess und setzen fort; andere simulieren Agent-Fehlverhalten (fremde Commits, verlinkte Artefakte, umgeschriebene Config, gelöschte Tests).
  • Abnahme: tests/test_e2e_dry_run.py bildet die DoD aus docs/SPEC.md §8 ab — vollständige CLI-Dry-Runs (Single und Parallel), Gate-Fail → Fix in derselben Session, Freigabe-Gates, Triage-Pfade, Crash-Resume, Dual Authoring, beide RED-Pfade.
  • GUI: FastAPI-TestClient-Tests auf Endpoint-Ebene (inkl. der Payload-Robustheitsmatrix) und ein abhängigkeitsfreier JS-Harness (tests/gui_js_harness.js), der das ausgelieferte app.js in node treibt — ein fehlendes node lässt Tests scheitern, nicht überspringen.
  • Lint: uv run ruff check . (Regeln E, F, W, I, UP, B; Zeilenlänge 100; py312). ruff format wird nicht erzwungen — große Teile des Baums sind nicht formatiert, und ADWs eigene Lane-Config gatet bewusst nicht darauf. In diesem Repo weder flake8 noch isort noch black verwenden.
  • Gate pro Änderung: roter Test → Implementierung → uv run ruff check . + uv run pytest → codex review --uncommitted, mit der P13-Rundenpolicy von Hand (Hinweis: --uncommitted nimmt kein Custom-Prompt-Argument an, die Dispositionen führt der Contributor selbst). P1 vor dem Commit fixen.
  • ADW auf sich selbst: .adw/config.yaml dieses Repos definiert eine einzelne backend-Lane mit den Gates ruff check und pytest (tdd: true) sowie GitHub-CI. Änderungen baut oft ADW selbst — wie man ein konvergierendes Issue schreibt, zeigen die Briefe in docs/briefs/.

18. Release-Prozess

Verbindlich, aus der Projekt-CLAUDE.md:

  1. Jeder Push nach main ist ein Release (SemVer 0.x): Feature-Push → Minor-Bump, reiner Doku-/Fix-Push → Patch-Bump.
  2. Version nur in pyproject.toml (project.version) erhöhen. adw/__init__.py liest sie aus den Paket-Metadaten; dort nie ein Literal pflegen (tests/test_smoke.py::test_version_matches_pyproject).
  3. CHANGELOG.md und CHANGELOG.de.md nachziehen (Keep a Changelog): die Unreleased-Sektion bekommt Nummer und Datum, Compare-Link ergänzen; neue Arbeit sammelt sich in einer frischen Unreleased-Sektion.
  4. git tag vX.Y.Z auf den Release-Commit, dann git push && git push --tags.
  5. Doku ist zweisprachig (P15): beide Sprachfassungen in derselben Änderung pflegen.

19. Bekannte Einschränkungen und offene Follow-ups

Bewusst akzeptiert (by Design):

Einschränkung Einordnung
Die git-Konfiguration des Ziel-Repos (Filter, Signierung) gilt als vertrauenswürdig. Vom Nutzer kontrolliert und außerhalb der Agent-Schreibpfade.
Codex' Read-only-Sandbox verhindert Schreiben, nicht Lesen außerhalb des cwd. Gemildert durch secret-freie Umgebung und abgeschaltete MCP-Server.
In der Entwurfsstufe liest der Codex-Autor denselben Checkout wie der parallele Claude-Autor. Worktree-Isolation würde die Phasen-Eingaben verbergen; der Claude-Entwurf wird validiert und der Checkout vor der Synthese zurückgesetzt.
Der Codex-Token-Rücksync hält seinen Lock nicht über das ganze Review. Sonst würden parallele Reviews minutenlang serialisiert; schlimmstenfalls ein einmaliges codex login.
Ein Crash zwischen CI-Re-Entry-Checkpoint und nächstem Poll kann ohne zweiten Fix-Versuch eskalieren. Begrenzt, auf der sicheren Seite.
Der Circuit-Breaker vergleicht exakte Texte — variierende Ausgaben (Zeitstempel) umgehen ihn. Dann greifen die harten Limits.
Der RED-Beweis hängt an Test-Pfaden, nicht am Inhalt; ein Test-only-Durchlauf, der auch Produktivcode schreibt, wird nicht erkannt; vor dem Testdurchlauf gibt es keinen grünen Basislauf. Inhalts-Unveränderlichkeit würde legitime Test-Reparaturen zu Eskalationen machen; verwässerte Tests bleiben dem Codex-Code-Review überlassen.
Lanes sind eine geschlossene Menge (backend, frontend); --parallel braucht beide. Bewusste Einfachheit; siehe §15.
Task-genaue Zuordnung im Trace ist nicht gebaut. docs/SPEC.md §6: Die Dispatch-Einheit ist der Workstream.

Offene Follow-ups (siehe docs/FOLLOWUPS.md):

  • #3 Nachweis der GUI-Antwortzeit (A4) an einem Lauf mit ≥ 2000 Tool-Knoten — wartet auf einen wirklich großen Lauf.
  • #6 Eine Lazy-Payload-Anfrage, die während eines Live-Region-Tauschs unterwegs ist, kann in einem abgehängten Element landen — braucht zuerst eine Reproduktion.
  • #9 Der Dirty-Check der Retention ist über mehrere Worktrees eines Laufs nicht atomar — nur mit --parallel erreichbar.
  • GUI-SPEC §7.2 A: Das Live-Update der Lauf-Liste ist noch nicht umgesetzt.
  • GUI 0.26.0 AC 5 (Referenz-Größenmessung) ist als unverifiziert vermerkt.

20. Glossar

Begriff Bedeutung
Lane Ein Workstream (backend / frontend) mit eigenem Worktree, Branch, Ports und SDK-Session.
Gate Ein Projektkommando aus der Config (Lint, Tests, …), vom Orchestrator mit Timeout ausgeführt.
Gate-Beweis gates_passed + gates_tree: Tree-Hash des vollständigen Worktree-Inhalts (inkl. untracked) über einen temporären git-Index.
RED-Stufe Initial-Build einer Lane mit tdd: true-Gate: Test-only-Durchlauf, danach beweist der Orchestrator die markierten Gates rot.
Entwurfsstufe / Synthese Phase 1–2: Claude und Codex entwerfen parallel; der Synthese-Agent führt zusammen und schreibt die Gate-Zusammenfassung.
Dispatch _dispatch_lane_fixes: Findings pro Lane gruppieren, Lane-State atomar vormerken (optional mit Budget-Erhöhung über mutate_staged), dann die reguläre Lane-Schleife.
Circuit-Breaker check_progress: dieselbe Fehler-/Finding-Menge wie in der Vorrunde → sofort eskalieren.
Vertagtes Finding Ein reines P3-Finding, das ein Fix-Lauf unberührt ließ; als Follow-up vermerkt und von späteren Dispatches und dem Breaker ignoriert.
Breakpoint Optionaler menschlicher Halt before_integration / before_push über die Freigabe-Mechanik.
Eskalation Kontrolliertes, endgültiges Laufende: escalation.md + phase=escalated + Exit 1.
Span Ein Start/End-Paar im Event-Log mit ID; Spans verschachteln sich über parent oder, bei Worker-Threads, über die Zeit.
Snapshot-Ref refs/adw/<run_id>/<seq>, ein Commit-Objekt, das einen Worktree-Stand für Schritt-Diffs pinnt.
Fail-open Eine Komponente, deren Fehler protokolliert und geschluckt wird, damit sie nie das Ergebnis eines Laufs ändern kann.
